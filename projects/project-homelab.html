From Media Server to Personal Cloud

I started with media streaming and expanded the lab into a platform for my own applications, shared sign-in, AI workflows, and storage. I use it to test changes and solve problems that come up when you run your own services.

Apps I built

  • Job application workspace. I built a tool that imports CVs into structured fields, suggests edits for a specific job, and exports a PDF. I accept or reject each suggested edit.
  • Vocabulary trainer. I built a tool that turns a term into a short explanation, flashcards, and links to related terms. Spaced repetition brings difficult terms back for review.
  • AI video generator. I choose a start and an end image, see the estimated cost, and submit a background job. The page shows progress until the short clip is ready.
  • Searchable knowledge base. AI assistants can save notes and transcripts through MCP. Keyword search and local embeddings help them retrieve relevant passages for later tasks.

Technical design goal

I designed this as a real-world learning environment, not a lab that only works on paper. The architecture separates public entry, compute and storage so I can experiment safely, keep services recoverable and work within the limits of quiet, low-power hardware at home.

What Runs On It

The main roles are edge traffic, shared application services, workers, and storage.

Cloud Gateway

CaddyCrowdSecWireGuardTLSGateway API
  • Caddy at the edge: Automatic TLS, strict security headers, structured logs, compression, and route-level rate limits.
  • CrowdSec: Filters suspicious traffic at the edge.
  • WireGuard: Used to protect traffic between infrastructure components.
  • Administrative access: Management access is separate from application traffic.
  • Security telemetry: Gateway logs and alerts inform monitoring and incident triage.

Application Platform

FastAPISQLAlchemySQLitePasskeysOIDCOAuth2JWT SSOLiveKitMCPTyper CLIPrivate PyPI
  • Unified backend control plane: FastAPI + SQLAlchemy + Alembic + SQLite drive authentication, permissions, app registration, audit logs, AI orchestration, and cross-app state.
  • Passwordless, federated login: I built an OIDC provider and an OAuth 2.0 consent flow. Users sign in with passkeys, and applications and AI assistants receive scoped tokens.
  • Real-time and generative surfaces: self-hosted voice/video rooms (LiveKit/WebRTC) and an AI keyframe video generator that turns a start and end frame into a short clip - both behind the same SSO and edge security.
  • Other custom apps. An app launcher brings together tools for web captures, item and payment tracking, agent activity, music intake, voice and video rooms, and QR codes.
  • Central app controls: A shared application registry lets me disable access to individual apps.
  • AI assistant bridge (MCP): AI clients connect through single sign-on and consent, the server mints a scoped token for them, and they get tools for tasks, research, calendars, mail and security briefs.
  • Administration dashboard. I can check how long agent runs take and what they cost.
  • Task workflow across CLI and MCP. I built a Python CLI that lets a coding agent pick up a task and log its progress. The agent can check service health through MCP, then record its result in the shared task log.

Agent + Worker Layer

ResearchTerm-masterySecurity-triageGovernance-triageInfra-monitoringInfra-repairQuality-checkDraftingCV-coachOllamasqlite-vecWhisperPlaywrightSharpSearXNG
  • Research agent: Researches the web through a private meta-search backend and headless browsing, then returns structured briefs.
  • Term-mastery agent: Generates summaries, flashcards, and remediation workflows for learning content.
  • Security triage agent: Correlates edge alerts, access logs, sessions, and approval-gated write actions for admin review.
  • Governance triage agent: watches internal session, permission, and account anomalies with a graded action policy - low-risk fixes auto-execute, high-blast-radius actions enter a human approval queue.
  • Infrastructure monitoring agent: runs probes across nodes, containers, temperatures, and backup freshness, then an optional AI layer triages findings into a recovery-aware signal feed. A paired repair agent proposes a bounded fix and only applies it after my approval.
  • Quality-check agent: verifies content summaries and crawls, spots login walls and empty captures, and tries one bounded rescue scrape before it refreshes the result.
  • Drafting and CV agents: one writes replies to a conversation for mandatory human review and never sends anything itself. The other reviews a CV, tailors it to a job posting and returns edits that I accept or reject.
  • Local AI: I use Ollama to run language models and generate embeddings. Local inference handles background and batch workloads. Hosted models handle latency-sensitive agent workflows.
  • Decision engine: A lightweight model scores or classifies text and flags potential prompt injection for review.
  • Agent memory and knowledge base: Combines full-text and vector search over curated notes, documentation, and transcripts, using local embeddings.
  • Video to transcript: a worker turns a video link into a timestamped, chunked transcript that agents can read, using human-written subtitles first and Whisper as the fallback.
  • Two run modes: Fixed pipelines handle predictable tasks, and adaptive model-driven workflows handle tasks that need more judgment.
  • Shared guardrails: Every agent runs behind kill switches, token/cost/runtime budgets, tool allowlists, concurrency caps, and blocked-action logging.

K3s Cluster

  • Traefik ingress: Host-based routing and a clean path to declarative microservice deployments.
  • Portainer: Cluster visibility and day-to-day Kubernetes management.
  • QR microservice: A React + Vite service running in K3s as the current reference workload for the cluster.

Storage + Media Plane (NAS)

TrueNASZFSJellyfinRadarr/SonarrImmichNextcloudNavidromeLidarrForgejoMinIO
  • TrueNAS SCALE + ZFS: Separate storage node with mirrored HDD bulk storage, SSD hot tier, and service-specific datasets.
  • ZFS memory tuning: I limited the filesystem cache to leave memory available for applications running alongside storage.
  • Full self-hosted media: Jellyfin with hardware transcoding, fed by a Radarr/Sonarr/Jellyseerr/Bazarr/Jackett acquisition pipeline with ClamAV scanning; Immich for photos; Nextcloud for files; Navidrome + Lidarr + Soulseek for music; Forgejo for Git hosting.
  • S3-compatible object storage: Dual MinIO tiers keep hot objects on SSD and move colder data to HDD through lifecycle rules.
  • Versioned backups. A nightly job copies core databases and service configuration. It keeps previous versions and records checksums.
  • Game server plan: I planned a containerized game server with persistent world data.
  • Power and cooling: I monitor power use and use drive temperatures to control airflow.

Lessons Learned

ARM has quirks

Not all Docker images support ARM64. Finding compatible alternatives and tweaking configs taught me to read docs carefully.

DNS is powerful

Managing records in Cloudflare and understanding how traffic flows made the whole system click.

Faster local speech

In a July 2026 test, a lighter text-to-speech engine cut response time from about 2.5 seconds to roughly half a second per sentence through the same gateway. The faster voice sounded less natural.

Cost-conscious infrastructure

Running on low-power devices and free-tier cloud taught me to optimize before scaling.

Security is a journey

Implementing SSO, token blacklisting, and audit logging taught me that authentication is more than just passwords.

Hybrid architecture complexity

Using Docker Compose and K3s together taught me to plan how workloads discover and reach each other.

Environment matters

Limited power, noise, and space shaped my hardware choices. I favored efficient components and measured how the system behaved under load.

Local AI has a hardware ceiling

I tested local models on a real research prompt. Responses took 4 to 20 minutes against a 10-second target. That led me to use local models for background tasks and hosted models when response time matters.

Works on Wi-Fi, fails on mobile

Every service timed out on roaming mobile data while Wi-Fi worked instantly. The cause was oversized TCP packets lost inside the carrier's tunnel. Capping the packet size at the edge fixed it, and the obvious suspect, HTTP/3, turned out to be a red herring.

Measure, then cool

I added fan control based on the warmest drive. The fans switch to full speed if a sensor fails. The readings recorded after the change were lower.
